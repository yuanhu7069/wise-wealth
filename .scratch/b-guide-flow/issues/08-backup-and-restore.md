## 完成记录（备份侧，2026-09-11）

`scripts/backup.sh` + `README` 备份恢复章节 + `.gitignore` 的 `backups/`，实测脚本 `.scratch/b-guide-flow/tmp-verify-08.sh`（第 1、2、3、6 节全通过，退出码 2 = 演练侧阻塞）：

- **产出**：`pg_dump --format=custom` → `backups/wise_wealth_YYYYMMDD_HHMM.dump` + 同名 `.sha256`。选自定义格式而非纯 SQL，是因为它**恢复时可校验、可选择、可并行**（`pg_restore --list` 能先证明档案可读）；实测该命令确实能列出 5 张业务表。
- **半截文件不留正式身份**：先写 `.part`，`pg_restore --list` 自检通过才改名——失败必须留下失败的痕迹，不能留下一个顶着正式名字的坏备份。
- **保留策略**：日备 7 份 + 周备 4 份，判据取**文件名里的时间戳**而非 mtime（拷贝与同步会改 mtime，文件名才是备份的身份）。实测：造 20 天合成备份 → 清理后恰好 7 + 4（周备取最近 4 个 ISO 周各一份），校验文件随备份一起清理。
- **篡改检测实测**：改动转储中 1 字节后 `sha256sum -c` 如实报错。
- **不进版本库**：`backups/` 进 `.gitignore`，`git check-ignore` 与 `git status --porcelain` 双向确认。
- **异地提醒**：脚本每次结束提示手工拷一份到云盘/另一台机器（arch §7：本地 + 异地各一份）。

## 延后记录（恢复演练，2026-09-11 苑问决定）

`scripts/restore-drill.sh` 已写完（备份 → 副本库恢复 → 抽验 → 副本库起服务验证，全程不写源库），但**演练本身没跑**：应用角色 `wise_wealth_user` 无建库权限（`rolcreatedb=f`），`CREATE DATABASE` 直接报 `permission denied to create database`（连接权限正常，只差建库权限）。现存库 `testdb` 属主是 `postgres`，应用角色对它也没有 CREATE 权限，无法顶替。

**需要实例管理员执行以下任一条，然后重跑 `scripts/restore-drill.sh` 即可**（脚本会把演练记录块打印成可直接抄进测试报告的格式）：

```sql
-- A. 一次性建好副本库（OWNER 不能省：PG15 起 public schema 归库主所有，不指定属主则恢复时建不了表）
CREATE DATABASE wise_wealth_backup_test OWNER wise_wealth_user;
-- B. 让脚本自建自用（权限更宽，但「备份→恢复→抽验」从此可零手工反复验证）
ALTER ROLE wise_wealth_user CREATEDB;
```

**为什么脚本不降级成「恢复进源库」**：那等于用恢复演练制造一次事故。缺权限时脚本打印上述 SQL 并以**退出码 3**（区分于失败码 1）结束 —— 阻塞不是失败，不该混为一谈。

**影响**：①README 的红线「恢复演练完成前不录入不可重建的真实数据」**继续生效**（这是 ADR-A-002 的兑现条件，prd-v1 红线 4）；②ticket 09（验收报告）仍被本项阻塞，其报告需把 AC-15 标为未完成而非跳过；③演练脚本的无权限路径已验证（退出码 3 + 可执行 SQL 提示），建库后是一条命令的事。

**切分理由：** 与 09（验收走查）**不合并**：①阻塞边不同——本 ticket 只需 05，可与 06／07 并行；09 需要 06／07／08 全部完成。合并会把本可并行的工作串行化。②验证方式不同：本 ticket 是脚本产出 + 恢复抽验，09 是人工走查 + 报告。
