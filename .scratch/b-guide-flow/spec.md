## Problem Statement

打开智策理财，只有 A 期留下的一个工程验证页——它证明「服务活着、数据库连得上」，但回答不了任何理财问题。

产品 PRD 的核心承诺（**2 分钟回答几个问题，拿到一张当月可照做的资金分配表**）目前完全没有兑现。替代做法是凭感觉安排工资：钱到账后随手分一分，既没有分账纪律，也说不出为什么是这个比例。结果是每个月都在重复同一个决定，且无法验证「分层理财决策工具」这个产品假设是否成立。

同时，A 期留下的三笔承诺悬在空中：业务端点没有鉴权（ADR-A-001）、有业务数据却没有备份策略（ADR-A-002）、埋点链路从未跑通。

## Solution

登录后走完 6 步问卷，拿到一份**可照做的方案**：每个账户每月转入多少、投资部分的大类比例、买入与再平衡的执行规则、落地建议与风险提示。方案基于收入、固定支出、现有存款与四个行为问题现场算出，不是模板套话。

方案可重新生成，每次生成保留为独立版本——收入变了就重算一版，旧版本仍在，供日后对比。

配套交付：单用户登录与会话管理、问卷逐题自动存草稿（中断可续）、模式库配置化（TOML，加模式=加文件）、分账引擎（纯函数，金例锁定）、埋点最小实现、备份脚本与恢复演练。

## User Stories

### 访问与鉴权

1. 作为唯一用户，我想用账号密码登录，以便我的收入与存款不被任何其他人看到
2. 作为用户，我想在会话过期后被送回原来正在做的事，以便不丢失问卷进度
3. 作为用户，我想在密码输错时看到明确原因，以便区分「密码错」和「被限流」
4. 作为用户，我想在连续输错时被限流保护，以便账户不会被暴力破解
5. 作为未登录访客，我想访问任何业务页面时被引导到登录页，以便知道需要先登录
6. 作为用户，我想登录后自动回到我原本要去的页面，以便不重新找入口
7. 作为用户，我想退出登录，以便在共用设备上结束会话

### 问卷

8. 作为用户，我想回答「这笔钱几年后要用」，以便系统知道这笔钱能不能进权益类
9. 作为用户，我想回答「100 万跌到 70 万的第一反应」，以便系统按我的真实行为而不是自我评价来配置
10. 作为用户，我想回答「收入稳定吗」，以便系统决定应急金该留几个月
11. 作为用户，我想记录社保、商保、房贷余额与需赡养人数，以便这些信息被留存供后续期使用
12. 作为用户，我想录入月收入、月固定支出、现有存款与理财目标，以便系统算出具体金额
13. 作为用户，我想一次只回答一个问题，以便不觉得这是一份长表单
14. 作为用户，我想每答完一步就自动保存，以便被打断后能接着答
15. 作为用户，我想重新进入问卷时停在我上次答到的位置，以便不用重答
16. 作为用户，我想在输入非法数字时看到具体错误，以便知道该怎么改
17. 作为用户，我想在有必答项没选时被明确拦住，以便不糊里糊涂跳过去
18. 作为用户，我想在重新生成方案时看到上次的答案预填，以便只改变化的数字
19. 作为用户，我想知道「房贷与保险本期不影响结果」，以便不误以为填了就会改变方案

### 推荐与模式选择

20. 作为用户，我想在答完后看到系统推荐哪个模式，以便不用自己研究七个模式的区别
21. 作为用户，我想看到推荐理由是一句人话，以便理解为什么推荐它
22. 作为用户，我想自己选最终用哪个模式，以便决定权在我
23. 作为用户，我想看到模式出处的可信度标识，以便知道它的来源是否可靠

### 方案

### 界面与可用性

## Implementation Decisions

### 分层与模块

沿用 A 期锁定的分层（handler / service / repo / domain），新增：

- **domain 层 · 分账引擎**：纯函数模块，输入「档案 + 模式配置」，输出「各桶金额 + L2 配置 + 推理链数据」。零 IO、零 HTTP 感知（ADR-B-004）
- **services 层**：`auth`（登录校验/签发/限流）、`profile`（问卷档案 upsert 与草稿步号）、`recommend`（L1 主推 + L2 匹配）、`plan`（编排引擎 + 版本化落库）、`analytics`（事件写入，失败不抛）
- **api 层**：新增 auth / profiles / plans / modes 四组端点；新增鉴权中间件与登录限流中间件
- **repo 层**：users / profiles / plans / analytics 四组数据访问
- **配置资产**：模式库 TOML（两份 L1 模式 + **四份 L2 配置**：三档阶梯 + 一份短久期现金覆盖），**构建期由 `build.rs` 扫描目录自动收录**并 `include_str!` 进二进制，启动时解析并校验。四份而非三份：`cash_only` 是「久期不足一年」覆盖档，与三档基础阶梯并列存放（此处的数量修正是实现期对规格的补全，原表述「三份」漏计了覆盖档）
- **模式阶梯是代码级规则**：`清仓/减仓 → 永久组合`、`不动 → 60/40`、`加仓 → 核心-卫星` 这三档映射是 RULE-015 这条业务规则本身，写在代码里；配置只提供每一档的具体比例。启动期交叉校验「阶梯引用的 L2 id 在库中齐全」，避免缺档要到用户点「生成方案」才暴露

前端：新增登录页、问卷页、方案页；首页改造为产品首页；新增统一 401 拦截与回跳。

### 数据模型（3 个迁移）

金额一律 `BIGINT` 分、字段名带 `_cents`；比例一律万分比整数；时间 `timestamptz`；主键 UUIDv7。

- **users**：用户名（唯一）、密码哈希（argon2）、tier（默认 free）、创建时间
- **profiles**（一行/用户，upsert）：`draft_step` + 六项问卷答案 + 三项金额 + 理财目标 + `questionnaire_completed`
- **plans**：L1/L2 模式、版本号、`is_active`、档案快照 JSON、推理链 JSON、创建时间；**部分唯一索引保证单一 active**（`UNIQUE(user_id, version)` + `UNIQUE(user_id) WHERE is_active`）——约束落在数据库层而非仅应用层
- **plan_buckets**：桶 id、名称、月转入金额、目标金额、备注
- **analytics_events**：事件名、payload JSON、发生时间；payload 只存枚举与步号，**金额永不入埋点**

### 引擎规则（产品核心，逐条可判定）

- **求解顺序**：固定支出桶 → 比例桶（基数 = 税后月收入）→ 规则桶 → 余量桶
- **一个模式至多一个余量桶**（四账户 = 投资桶；50/30/20 无余量桶，储蓄桶兼作投资桶）
- **应急月数**：收入稳定性映射 很稳 3 / 一般 6 / 波动大 9 / 自由职业 9；需赡养人数 > 0 上浮一档（3→6→9→12，上限 12）
- **必要月支出** = 模式声明的桶之和（四账户 = 工资桶 + 消费桶；50/30/20 = 必要桶）
- **应急目标** = 应急月数 × 必要月支出；**缺口** = max(0, 应急目标 − 现有存款)
- **规则桶月转入** = 缺口 ÷ 24，四舍五入到百元（half away from zero）；缺口为 0 时转入为 0，份额落入余量桶。**取整只做一次**：先算商再取整会让中间结果被放大一个档（缺口 ¥1,199.88 ÷ 24 = ¥49.995，先四舍五入成 ¥50 再取整就变成 ¥100/月，正确结果是 ¥0/月）
- **固定支出超过必要桶额度**（无固定支出桶的模式，如 50/30/20）→ 给出 `FixedExceedsNecessary` 提示，不改金额（源自 prd-v1 §7.3 业务边界表）
- **达标是状态不是提示**：方案页的达标文案由 `is_met` + `surplus_cents` 构成，不额外塞一条 Notice —— 同一事实两个来源迟早会不一致
- **safety_first**：余量 < 0 时 → 投资桶归零 → 仍不足则缩减规则桶转入至 0 → 仍不足则方案标记「收入不足以覆盖当前结构」。**任何桶不得出现负数**
- **现有存款**整体视为备用账户余额；超出应急目标的部分仅作展示（「投资账户已有家底」），不参与月度分配
- **L2 匹配**：回撤反应定基础档（清仓/减仓观察 → 永久组合 25% 权益；不动 → 60/40；加仓 → 核心-卫星 75%）；久期 1-3 年降一档（下限永久组合），**1 年内覆盖为现金类 100% 并标注原因**；收入稳定性不参与 L2
- **L1 主推**：现有存款 < 3 × 月固定支出 → 主推四账户（先建分账纪律与应急金），否则主推 50/30/20（结构简洁）；用户可选任一

### 问卷状态机（来自原型，逐字对照验收）

```
步 1 久期(单选5) → 步 2 回撤反应(单选4) → 步 3 收入稳定性(单选4)

操作栏：步 1 = [下一步]；步 2-5 = [上一步][下一步]；步 6 = [上一步][生成方案]
```

### 界面决策（来自原型 design-v1.html，均已苑问走查确认）

- **设计 Token**：取值唯一来源为 design 基线 §5（松墨绿主色 + 暖白底 `#FAF9F7` + 次级底 `#F2F0EC` + 图表六色板），实现期零自创色值
- **暗色**：class 策略（`.dark`）+ 跟随系统默认 + 手动三态切换（跟随系统/亮/暗），偏好存 localStorage（非敏感）
- **向导操作栏**：**固定于视口底部**，位置不随步骤内容高度变化；视觉分两条带——操作带沿用页面底色（读作内容区的一部分）、声明带用次级底色（读作独立声明条）
- **向导顶部工具行**：左「返回首页」，右「每步自动保存草稿，中断后可恢复」
- **免责声明**：默认仅一行简述 + 「完整声明」可展开 PRD §13.1 原文；承载位置 —— 首页/登录页 = 站点页脚，问卷页 = 固定操作栏内、按钮下方（问卷页不显示站点页脚），方案页 = 五段之「风险提示」。**移动端启用更短文案变体 @11px 以保证单行**（对基线 §5.2 的 12px 下限属显式偏离，已记入 RULE-020）
- **尺寸铁律**：容器尺寸由内容撑开（`min-height` + `padding`），禁止 `height` + `line-height` 配对装可换行文案；禁止用文字充当图标占位
- **图标**：lucide 线性图标内联 SVG，不引入外部依赖

### 鉴权实现

单用户账号密码；凭证由种子脚本从环境变量写入（无注册页、无找回，忘记即重跑种子脚本）；argon2 哈希；JWT（HS256，密钥走环境变量）存 HttpOnly + SameSite=Lax Cookie，有效期 30 天；登录失败限流（内存滑动窗口，1 分钟 5 次）；`from` 参数只接受以单个 `/` 开头的站内路径（防开放重定向）。

### 运维（兑现 ADR-A-002）

首次业务表落地必须同批交付：`backup.sh`（`pg_dump` 自定义格式 + SHA256 校验 + 保留策略）与**一次实际恢复演练**（恢复到副本库并抽验行数与金额），演练记录写入测试报告。**恢复演练完成前，不录入不可重建的真实数据。**

## Testing Decisions

### 好测试的标准

只断言**外部可观察行为**：引擎断言「输入档案 + 模式 → 输出金额」，API 断言「请求 → 响应码 + 信封内容」，不断言内部函数调用或私有结构。金额断言一律精确到**分**并逐项比对，不使用容差——分账算错是产品级事故。

### 测试接缝（seams）

拟用**两个自动化接缝 + 一个人工走查**，接缝数量刻意保持最少：

1. **分账引擎（主接缝，最高点）** —— 纯函数，零 IO，一次覆盖产品最大的风险面。用三个金例驱动：
   - 金例 A（正常）：月收入 12,000 / 固定支出 4,500 / 存款 24,000 / 久期 5-10 年 / 回撤不动 / 收入波动大 / 赡养 1 人 → 四账户 4,500 / 3,600 / 3,100 / 800；L2 = 60/40；应急当前约 3.0 个月
   - 金例 B（达标）：同 A 但存款 150,000 → 规则桶归零、投资桶 3,900、家底展示 52,800
   - 金例 C（不足）：月收入 8,000 / 固定支出 7,000 → 投资与备用均归零、带「收入不足」标记、**无任何负数金额**
   - 另加：50/30/20 同档案、久期 1 年内（现金 100% + 原因标注）、÷24 舍入边界（含百元取整 half-away-from-zero）、赡养上浮档（3→6→9→12 封顶）、万分比计算无浮点
2. **HTTP API** —— 鉴权边界与数据读写。用例：无 Cookie 访问每个业务端点 → 401；凭证错 → 错误码信封；第 6 次失败 → 429；`from=//evil.com` → 丢弃；步保存幂等（重复提交不推进版本）；方案生成两次 → 版本 1/2 且 active 唯一；埋点写入失败不阻断主流程
3. **人工走查**（不自动化）：四页五态、375px 与桌面双端、暗色三态、草稿断点恢复、401 回跳、320/375/768/1280 四档溢出扫描零命中、双主题对比度达标

### 参照先例

- A 期 `services/` 层单测（现有 10 个 `#[test]`）是引擎单测的直接先例——同样「金例驱动、断言精确值」
- A 期的端点实测（curl + 信封断言）是 API 用例的先例
- A 期用 playwright-core 做过真浏览器断言（暗色/reduced-motion 双上下文），界面项沿用该方法

> **需要确认**：以上接缝是否符合你的预期？特别是「引擎为单一主接缝、界面只做人工走查」这个取舍——若你希望界面也进自动化（playwright 断言进 CI 式流程），现在说成本最低。

## Ticket 切分决策（记录用，便于后续排查）

> 实施过程中若发现「某张 ticket 为什么这么大／为什么依赖那张／为什么不做成垂直切片」之类的疑问，先查本节。决策记录保持在 tickets 旁边，改切分时同步更新本节。

| # | 决策 | 理由 | 被否决的备选 |
|---|------|------|-------------|
| **D1** | **01（引擎）刻意不做成垂直切片**——只有 domain 层与单测，无 API/UI | ①它是产品核心，金额算错属产品级事故；②它是本规格的**主测试接缝**（纯函数、零 IO，金例可一次覆盖最大风险面）；③不依赖任何其他 ticket，可最早开工、最早退役风险。**代价**：本 ticket 不可演示，只能以 `cargo test` 验证 | 折进 05——会让 05 超出一个上下文窗口，且引擎与页面两类问题混在一起验收 |
| **D2** | **01 与 02 之间不设阻塞边** | 一个管算法、一个管数据与权限，交集只有「档案」这一数据结构，在 04 才汇合。两者可并行或任意顺序 | 让 02 阻塞 01（或反之）——制造出并不存在的依赖，拖慢开工 |
| **D3** | **原「方案生成与展示」拆成 05（生成 + 方案页）与 06（版本化 + 首页双形态）** | 合并版含两张表、生成接口、五段页面、首页改造、版本化五件事，超出一个上下文窗口；拆后 05 是**最短可演示路径**（生成一次即可看到方案），06 是其上的增量 | 不拆——单 ticket 过大，实现中途上下文耗尽的风险高，且失败时难以判断是哪部分没做完 |
| **D4** | **07（埋点）独立成 ticket，而非散在各 ticket 里埋** | 埋点是**一层横切能力**（表 + 服务 + 调用点），集中做完可用一条 SQL 验证；分散则每张 ticket 的验收都要重复验证同一张表。阻塞于 05 因为 5 个事件里有 2 个要有方案流程才存在 | 每个 ticket 各自埋自己的事件——验收重复，且事件命名容易各写各的 |
| **D5** | **08（备份）与 09（验收）不合并** | ①阻塞边不同：08 只需 05，可与 06／07 并行；09 需要 06／07／08 全完成。合并会把可并行的工作串行化。②验证方式不同：08 是脚本产出 + 恢复抽验，09 是人工走查 + 报告 | 并为「收尾」ticket——牺牲并行度，且两类证据混在一张 ticket 里不易追溯 |
| **D6** | **不设 prefactor ticket** | 实施前核对过地基：`ErrorCode` 已含 `UNAUTHORIZED` 与 `RATE_LIMITED`（限流无需新错误码）；前端 `api.ts` 已具备信封与 errorCode 类型；`config.rs` 已有必需环境变量校验框架。移除 A 期 Token 样例区归入 06（它本就是「首页改造」的一部分） | 为「移除 Token 样例区」单列一张清理 ticket——增加协调成本而无独立价值 |
| **D7** | **编号顺序 = 依赖顺序（阻塞者在前）** | 本地 tracker 的 frontier 规则是「扫描 `issues/` 中未完成、未被阻塞、未被认领的文件，编号最小者优先」，因此编号必须让可开工的排前面 | 按模块分组编号——frontier 会挑到被阻塞的 ticket |

**并行可能性**（供排期参考）：01 与 02 可同时开工；05 完成后，06 / 07 / 08 三者互不阻塞，可并行。
