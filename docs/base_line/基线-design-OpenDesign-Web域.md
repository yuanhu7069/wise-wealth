> **用途**：当某个项目的界面**交由 Open Design MCP 生成**时，由**我**把本文档交给 AI。
> **给 AI 的指令（最高优先）**：**本文档是本项目的 design 基线，界面设计严格遵循本文档。**

> **本文档的第一读者是 AI，第二读者是我自己。**
> 本基线**不定义任何视觉内容**——数值由 Open Design 生成产出。它只管一件事：**让生成出来的设计可控、可复现、可落地。**

## 0. 定位与使用方式

**本文档是本项目的 design 基线**——界面设计严格遵循本文档。

### 0.1 边界（与另外两份基线的分工）

| 文档 | 管什么 | 不管什么 |
|------|--------|---------|
| `基线-PRD-Web域.md` | 做什么、为谁做、做到什么算完 | 长什么样、用什么技术 |
| **本文档（design）** | **设计怎么生成、生成后怎么固化、落地后怎么验收** | 代码结构、技术栈、数据存储、接口设计；**具体视觉值**（那些由 Open Design 产出） |
| `基线-arch-Web域.md` | 用什么技术、怎么组织代码、性能与安全红线 | 视觉与交互细节 |

**三条硬边界**：
1. 本文档**不写技术选型**（框架、组件库、状态管理、构建方式）——那些归 arch；
2. 本文档**不写业务规则**（什么能做什么不能做）——那些归 PRD；
3. 本文档**只做一件事**：让 MCP 生成出来的设计**可控、可复现、可落地**。

### 0.2 适用范围

- **适用**：界面交由 **Open Design MCP 生成**的项目。
- **不适用**：设计不由 Open Design 生成的项目（无生成环节，本文档无可治理的内容）。

### 0.3 本文档不覆盖的内容（风格相关的取舍归实例）

- **Token 与视觉规则本身**——色值、字阶、间距、圆角，一律由生成的产物给出，本文档不含任何数值；
- **风格相关的取舍**——装饰密度、字重档位、色值要不要语义化等；这些取决于具体 design system 与本项目的页面类型，换一个项目结论就变，**归实例**；
- **与具体业务绑定的验收项**——归 PRD / 实例文档。

> **分界线**：**风格无关的合规项进本文档（§5），风格相关的取舍归实例（§5.4）。**
> 判断口诀仍是那句——**换一个项目，这条还成立吗**。成立就在基线，不成立才给实例。

> 归实例的部分**由我在实例文档中给出**；
> AI **不得自行从其他来源套用**，也不得假设存在某份"默认文档"可以参照。

## 1. 核心机制：设计真源不在文档里

**这是本文档与前两类设计流程最根本的差别**：真源既不在基线文档里，也不是一份已存在的外部文件，而是**一次尚未发生的生成动作**。

| 阶段 | 真源在哪 | 这个阶段的风险 |
|------|---------|--------------|
| **生成前** | design system（`designSystemId` / direction / 我提供的 DESIGN.md）——**实例必填** | 不固定就生成 → 每次结果都不一样，无从验收 |
| **生成中** | Open Design 项目内的 artifact / 文件 | 只存在 daemon 侧，**Git 里没有**；daemon 重装、清库、换机器即丢 |
| **落地后** | **代码库内的 tokens 文件与组件** | 不落地 = 项目永远没有设计真源 |

### 1.1 由此推出的三条硬要求

1. **生成前必须固定 design system**——没有视觉基准的生成等于抽奖；
2. **生成后必须固化进 Git**——这是把真源搬进项目的唯一一步，漏了就白生成；
3. **落地产物必须自包含**——不引用 Open Design 运行时、不依赖 daemon，项目能脱离它继续跑。

> 第 2 条最容易被跳过：artifact 在预览里看得见，就以为设计已经"有了"。
> 但只要它没进代码库，下一次 AI 打开项目时**看不到任何设计真源**，只能重新生成——必然漂移。

## 2. 生成前：必填参数与外部服务立场

### 2.1 必填参数（由实例给出；未给则 AI 必须停下来问我，不得自行选）

| 参数 | 说明 |
|------|------|
| **design system**（`designSystemId` / direction） | 视觉基准。可以是内置品牌库中的某一个，也可以是我提供的一份 DESIGN.md |
| **skill / plugin**（`skillId`） | 生成什么形态：prototype / deck / dashboard / landing page … |
| **fidelity** | 生成保真度档位 |
| **customInstructions** | 追加约束。**必须落盘进 Git**（见 §4）——它是生成提示词的一部分，只写在对话里就不可复现 |

> 固定这几个参数的目的只有一个：**让同一次需求可以重新生成出同样的东西**。
> 参数没固定就开生成，等于把设计结果押在一次不可复现的调用上。

### 2.2 外部服务立场（Open Design daemon + MCP server）

Open Design 是**外部独立服务**（本地守护进程 + MCP server），按 arch 的外部中间件立场处理：

- **不假设它已安装**、不主动探测、不把安装步骤写成前置任务；
- 开始前**只做连通性验证**；
- **连不上 / 工具不可用 → 停下来报告我**；
  ⚠️ **不得改用自己手搓设计、不得改用其他来源**——那等于擅自更换本项目的设计来源；
- 生成走 BYOK，**会消耗模型额度**：每次生成前明确这是一次真实调用，不批量重跑；
- 工具名与参数随版本变化较快，**以实际安装版本的帮助信息为准**，不凭记忆写死命令。

---

## 3. 生成中：流程与红线

1. **复用同一个 Open Design project 迭代**，不要每次新建——新建会丢掉对话上下文，是漂移的主要来源；
2. 迭代用**对话式修改**（"把主色换掉""这屏密度太高"），**不从零重生成**；
3. 生成出的 artifact 在固化前一律视为**草稿**，不得据此写业务代码；
4. 草稿阶段的 lint（如 `od_lint_artifact`）只用于筛选草稿，**不能替代落地后的验收**。

---

## 4. 生成后：固化与落地（P0）

这是本文档最关键的一节。

| 动作 | 产出位置 | 要求 |
|------|---------|------|
| **搬进代码库** | 实际代码：tokens 文件（接 arch 技术栈的 Tailwind v4 `@theme` 变量或等价形式）、组件 | **必须纳入 Git** |
| **留快照** | `docs/design/` 下存生成物副本 | 同上 |
| **记录生成元数据** | `docs/design/生成记录.md` | 同上 |

**生成记录必填项**：design system / skill / fidelity / customInstructions / 生成日期 / 工具版本。

> 记录元数据的意义：**半年后我能回答"这套界面是怎么来的"**。
> 参数没记，产物就只能当黑盒用——想改只能重新生成，而重新生成的结果未必一致。

- **落地后真源 = 代码库**。后续改动直接改代码；只有需要重新设计时，才再走一次生成流程，并留新一份快照与记录。
- **可退出性**：项目运行**不依赖 Open Design**。daemon 停了、机器换了、工具不再维护，已落地的设计照常可用。

## 5. 验收：三道闸门

> **先分清「选择」和「校验」**：
> **好不好看、合不合适 = 选择**（我做，用对比法：并排生成 2-3 个候选，选"别扭最少"的那个）——**不进验收清单**。
> **对不对、全不全、能不能用 = 校验**，下面三道闸门全部属于校验，**没有一项需要审美判断**。

### 5.1 T0 · 生成前（参数闸门）

| 判据 | 不通过会怎样 |
|------|------------|
| 参数四件套已固定（§2.1） | 没基准就生成 = 抽奖，后面无法验收 |
| `customInstructions` 已落盘进 Git | 只留在对话里则不可复现 |

- 执行者：AI 自查；**未达标不得开生成**。

### 5.2 T1 · 草稿验收（产物闸门，本文档独有）

> **这一层是本文档与前两类设计流程最不同的地方**：那两类的真源是现成的，没有"草稿"阶段；这一类的产物在固化前**什么都不算**，必须先过这一关。

**A · 一致性（可自动，不依赖审美）**

产物应与**它自己声明的 design system** 一致——token 值逐项比对即可。
对不上 = 这次生成没有落在声明的系统上，判为失败或漂移。

**B · 完整性（风格无关，跨项目成立）**

| # | 判据 | 说明 |
|---|------|------|
| 1 | **页面五态齐全** | 空态 / 加载 / 错误 / 空结果 / 正常。**生成物默认只有正常态**，这是生成式设计最大的缺口 |
| 2 | **极端数据不破版** | 金额超长、标题超长、列表 0 条与海量、负数。生成物只在"理想数据"下好看 |
| 3 | **中文渲染可用** | 字重够不够、字距挤不挤 |
| 4 | **自包含** | 不引用外部资源、不依赖 daemon 才能渲染 |
| 5 | **无障碍** | 对比度达标、键盘可达 |
| 6 | **数值展示**（项目有数值时） | 等宽、千分位、右对齐 |

- 执行者：可自动的部分自动跑，其余**我按表勾**；
- **未通过 T1 的产物不得落地**（草稿不是交付物）。

### 5.3 T2 · 落地验收（代码库闸门）

- **一致性判定**：实现结果与**已固化的 tokens / 组件**不一致之处，必须能在**本地化调整清单**里找到；**找不到的即为违规**；
- **未列入本表的项一律照生成的产物执行，AI 不得自行发挥**；
- ⚠️ **CI 不放生成动作**：生成耗时长（数十秒至数分钟）、依赖外部服务、结果不保证一致，挂进 CI 必然不稳定。**CI 只跑 T2，只验已落地的产物。**

| 调整项 | 生成原值 | 本项目值 | 理由 |
|--------|---------|---------|------|
| 例：主色 | `#533AFD` | `#4A6B57` | 品牌色须与我的其他产品一致 |
| 例：中文字重 | 300 | 400 | 微软雅黑细体在 Windows 偏糊，加一档 |

### 5.4 风格相关的取舍归实例（提醒清单，**不是禁令**）

> 以下几项**取决于具体 design system 与本项目的页面类型**，换项目结论就变——按 §0.3 的分界线归实例，基线不预先划线。
> 默认仍按生成产物执行；列出只表示这几项实测容易踩坑。

| # | 项 | 为什么建议确认一下 |
|---|---|---|
| 1 | 商业字体是否可用 | 品牌类 design system 常用商业授权字体；拿不到会静默 fallback，出现「写着 A、渲染成 B」 |
| 2 | 颜色有没有承载规则 | 品牌库多用 `ink` / `ruby` 这类命名，名字不承载规则。若本项目有靠颜色表达语义的场景（涨跌方向、状态等级），必须在调整清单中显式指定 |
| 3 | 中文字重与字距是否要加档 | design system 多为英文产品，常见「细体大标题 + 负字距」；中文场景通常需加重一档、字距收敛 |
| 4 | 装饰密度与页面类型是否匹配 | 让人干活 / 看数据的页面与让人被说服的页面答案相反，由实例判断 |

## 6. 红线

1. **未固定 design system 就生成**；
2. **产物未固化进 Git 就开始写业务代码**；
3. **落地代码依赖 Open Design 运行时**（引用其 CDN / 依赖 daemon 才能渲染）；
4. **服务不可用时自行手搓设计**或改换其他设计来源；
5. **每轮迭代都新建 project**，导致上下文丢失；
6. **customInstructions 只留在对话里**，不落盘；
7. **在 CI 中跑生成**；
8. **把草稿 artifact 当作交付物**；
9. **草稿未过 T1 就落地**（§5.2）——生成物默认只有 happy path，**五态与极端数据补齐后才算完成**。

---

## 7. 给 AI 的指令（硬约束）

1. 界面设计遵循本文档；视觉数值一律取自**已固化的产物**，不自行发明；
2. 必填参数（§2.1）**未给全时，停下来问我**，不自行选一个开跑；
3. 服务不可用时**停下来报告**，不降级、不绕过、不换来源；
4. 每次生成后**立即固化进代码库**并补生成记录，不等到"最后一起整理"；
5. 迭代走对话式修改，**不重新生成整个项目**；
6. 调整清单外的项**照产物执行**，不按自己的审美改动；
7. 产物**先过 T1 再落地**（§5.2）；缺五态、缺极端数据处理的，**补齐后再落地**，不把 happy path 当完成品。

---

## 8. 一句话收口

> **生成前固定参数 → 草稿过 T1 → 固化进 Git → 落地后真源在代码库。**
> 这四步里漏任何一步，这套设计就不可复现、不可验收。
