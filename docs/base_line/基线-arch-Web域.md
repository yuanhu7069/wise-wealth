## 0. 定位与核心决策

> 定位：苑问 **Web 类项目**的全栈技术宪法。所有 Web 项目的前后端代码必须遵守本规范。
> 核心决策：**强类型优先、编译期可验证优先、单一可部署产物优先。**

### 0.0 本基线的边界：锁定什么 / 不锁定什么【元规则 · 优先于全文】

**一份基线会被多个项目复用。凡"换个项目就可能需要改"的内容，一律不进基线，留给 `arch-A-{应用名}.md` 实例文档。**

| | 内容 | 归属 |
|---|---|---|
| ✅ **基线锁定** | 技术栈与版本、分层方式与职责边界、错误处理与响应契约、数据层用法与迁移工具、鉴权原则、安全红线、金额/时间等类型约定、代码审查清单、AI 生成硬约束 | 本文件 |
| ❌ **基线不锁**（留给实例） | 具体部署环境（WSL / 云 / NAS / Docker）、数据库实例位置与连接参数、代码存放路径、编辑器与工具链接入方式、备份的具体介质与频率、缓存是否引入、上云方案、具体业务表结构 | `arch-A-{应用名}.md` |
| 🔶 **基线给原则，实例给落地** | 备份（基线：必须异地 + 必须演练恢复；实例：落到哪个网盘/机器、几天一次）、性能（基线：必须定义可测量指标；实例：具体数值）、兼容性（基线：必须声明支持范围；实例：具体版本列表） | 两边都写，互补 |

> **判定口诀**：问一句「**换一个项目，这条还成立吗？**」
> 成立 → 进基线；不成立 → 进实例；只有目标成立、具体数值不成立 → **基线写原则、实例写数值**。

> ⚠️ **已犯过的错（留档，防止再犯）**：v0.1 讨论期曾把「代码放在 WSL 哪个目录」「PostgreSQL 装在 WSL 还是 Windows」「用哪个编辑器连接」列为待确认项。
> 这三条全部是**项目级/机器级**问题，与架构约束无关。
> **基线唯一与"代码位置"有关的约束是：代码必须纳入 Git 版本管理。**

### 0.1 标签机制【继承老师版最值钱的机制】

- **【原则】**：无论技术栈如何变化都必须遵守（换语言换框架也不变）；
- **【实现】**：当前技术栈（**Rust + axum / Next.js**）下的具体实现方式。

> **为什么重要**：技术栈一定会升级（axum 0.8 → 0.9、Next 16 → 17、甚至换语言），但原则不该跟着改。
> 老师案例的 arch 从 v1.0 演进到 v4.0，靠的就是"实现随便换、原则不动"。
> **未来换技术栈时，只改【实现】段落，【原则】整章保留。**

### 1.3 版本兼容核查结论（2026-09-07 已查证）

| 组合 | 结论 |
|---|---|
| Next 16.3.4 + React 19.2.8 | ✅ 官方推荐搭配，App Router 即用 React 19.2 |
| TypeScript 7.0.2 | ✅ 可用，但**有三个硬变更必须处理**（见下） |
| ESLint + typescript-eslint + TS7 | ❌ **不兼容**（TS7 GA 未发布 programmatic API，7.1 才有）→ **前端不用 ESLint，改用 Biome** |
| Tailwind 4.3.3 + shadcn 4.21.0 | ✅ 官方主推组合 |
| Rust + axum 0.8 + sqlx | ✅ 生态成熟，2026 后端默认 |

**TypeScript 7 的 tsconfig 硬变更（会直接编译失败，必须显式处理）**：

1. `strict` **默认为 true**（不写也开启）；
2. `types` **默认为空数组** —— `@types/node` 等**必须显式列出**；
3. `rootDir` 默认为 `./`（可能影响输出结构）；
4. `target: es5`、旧式 `moduleResolution`、`baseUrl` **直接编译失败**，必须改用新版写法。

**为什么选 Biome**：Next 16 已移除 `next lint`；typescript-eslint 与 TS7 不兼容（官方标记 not planned）。Biome 一个二进制搞定 lint + format，**完全绕开这个坑**，一人项目省心得多。

### 1.4 仓库结构【实现】

**单仓（Monorepo）**：

```
{项目名}/
├── server/          # Rust 后端（单一 binary crate）
├── web/             # Next.js 前端
├── docs/            # prd-A / design-A / arch-A / PLAN / test-report
└── README.md
```

**理由**：一次 clone 拿到全部；前后端契约同步演进；一个目录可备份。**代价**是仓库略大，但 OPC 一人维护利大于弊。

> 若将来需要把后端拆成多个 crate（`api` / `domain` / `db`），改用 cargo workspace，并写 ADR 说明。

## 2. 架构决策记录（ADR）【原则】

所有重大技术决策必须以 ADR 形式记录。**新增技术栈、改变分层、改变数据模型范式，都必须写 ADR。**
模板：`【状态】/【上下文】/【决策】/【后果（正面+负面）】`

### ADR-001：为什么后端用 Rust + axum

【状态】已接受（2026-09-07）
【上下文】一人公司，无人维护；项目有真实数据资产（家庭账目）；我在**持续学习 C/C++ 底层**（所有权/生命周期/内存模型的心智模型正在建立）。
【决策】后端用 Rust + axum + tokio。
【后果】
- 正面：**单二进制部署**（`cargo build --release` 一个文件，完美符合 OPC"一条命令启动、一个目录可备份"）；内存占用低（60-90MB）；**类型系统与编译期检查能拦住 AI 生成的大部分错误**；我在学 C，能读懂并改对 AI 写的 Rust 代码
- 负面：AI 生成 Rust 成功率客观低于 TS/Python；`cargo build` 反馈循环比脚本语言慢；学习曲线陡（**四个"新"叠加**：Rust + Next 16 + TS7 + Tailwind 4）

### ADR-002：为什么用 sqlx（SQL-first）而非 sea-orm / loco

【状态】已接受
【上下文】一人维护，需要长期可维护与可迁移；AI 容易生成过度抽象的 ORM 代码。
【决策】用 sqlx，优先 `sqlx::query!` / `query_as!` 宏（**编译期连接真实数据库校验列名与类型**）。
【后果】
- 正面：**SQL 写错在编译期就失败**，不是运行时；无隐藏的 N+1 魔法；迁移脚本即真相
- 负面：要手写 SQL；开发时需本地可连的 PG（或用 `sqlx prepare` 离线模式提交 `.sqlx` 缓存）
- **要求**：`.sqlx/` 目录**必须提交 Git**，否则 CI/换机编译失败

### ADR-003：为什么数据库默认 PostgreSQL

【状态】已接受
【上下文】数据库为**独立部署**（不由本基线操心实例位置）；项目含理财类等不可再生数据。
【决策】默认 PostgreSQL，不用 SQLite。
【后果】
- 正面：并发与扩展性好；支持全文检索（`pg_trgm`）、JSONB、窗口函数；备份用 `pg_dump` 成熟可靠
- 负面：需要独立数据库服务（**部署细节归实例层**）

### ADR-004：金额用 `i64` 存最小货币单位（分），全链路禁止 float

【状态】已接受
【上下文】理财/记账类应用。`0.1 + 0.2 != 0.3` 在财务场景是**正确性问题**，不是精度问题。
【决策】数据库 `BIGINT`，字段单位=分，字段名带 `_cents` 后缀；Rust 侧 `i64` 运算；**全链路禁止 `f64`/`f32` 参与金额**；仅在展示层格式化为 `¥1,234.00`。
【后果】
- 正面：无浮点误差；合计对账可复现；序列化简单（整数）
- 负面：涉及费率/汇率等小数运算需显式处理进位与舍入（**统一 round half away from zero，且必须写测试**）
- **例外**：若某项目确需 4 位小数（如基金份额），在 `arch-A` 中声明并写 ADR 改用 `rust_decimal::Decimal`

### ADR-005：为什么权限校验必须在服务端

【状态】已接受
【上下文】前端隐藏按钮 ≠ 有权限。任何前端校验都可绕过（直接调 API）。
【决策】**每个 API 端点必须在服务端校验身份与权限**；前端权限控制只是体验优化，不作为安全边界。
【后果】
- 正面：越权不可能发生（家庭共用场景尤其重要）
- 负面：每个端点都要写校验（用 axum 中间件 + Extractor 降低重复）

### ADR-006：为什么统一响应信封 + 集中错误码

【状态】已接受
【上下文】"余额不足"这类**业务错误无法用 HTTP 状态码表达**；前端需要稳定的机器可读码来映射文案。
【决策】所有 API 响应使用统一信封（§6.1），错误使用集中错误码表（§6.2）。
【后果】
- 正面：前端错误处理可统一封装；errorCode 可观测可统计
- 负面：HTTP 码与业务码并存，轻微冗余

### ADR-007：为什么强制分层（handler / service / repo）

【状态】已接受
【上下文】AI 生成 axum 代码最常见的形态是"业务逻辑全写在 handler 闭包里"——能跑，但无法测试、无法复用、规则散落。
【决策】强制三层：`handler`（HTTP 协议）/ `service`（业务规则）/ `repo`（数据访问）。
【后果】
- 正面：业务规则集中在 service（对应 PRD 的 RULE 编号），可单测；换库只动 repo
- 负面：小功能也要建三层，略啰嗦

### ADR-008：为什么前端走 Next 服务端代理（BFF）而非浏览器直连 Rust API

【状态】已接受
【上下文】前后端分离后，Cookie 跨域、CORS、错误格式、鉴权回跳最容易各写各的。
【决策】浏览器 → Next.js（Route Handler / Server Action）→ Rust API（内网）。**前端代码禁止直接拼后端域名发请求**。
【后果】
- 正面：无 CORS 问题；Cookie 在同域内转发；Server Component 可直接取数（少一次客户端往返）；后端地址不暴露
- 负面：多一跳（内网延迟可忽略）；Next 侧需维护代理层

5. 项目根目录禁止堆积临时脚本，一律放 `scripts/`。

## 4. 后端架构规范（Rust + axum）

### 4.1 分层与职责【原则】

| 层 | 职责 | **禁止做的事** |
|----|------|--------------|
| **handler** (`api/`) | 解析参数（Extractor）、调 service、转响应 | ❌ 写业务规则 ❌ 直接写 SQL ❌ 直接拿 `PgPool` 查询 |
| **service** (`services/`) | 业务规则、事务边界、权限语义 | ❌ 感知 HTTP ❌ 直接拼 SQL |
| **repo** (`repos/`) | SQL 与数据读写 | ❌ 写业务判断（"余额够不够"属于 service） |
| **domain** (`domain/`) | 领域模型与不变量 | ❌ 做 IO |

**AI 提示**：如果你在 `api/*.rs` 里写 `if ... else` 判断业务规则——**停，挪到 service。**

### 4.2 API 设计规范【原则】

1. **RESTful**：资源用复数名词（`/api/v1/transactions`），动作用方法表达；
2. **版本前缀**：所有 API 带 `/api/v1/`；
3. **分页必带**：所有列表接口必须 `page` / `page_size`，**禁止一次返回全表**；
4. **排序白名单**：`sort` 字段必须白名单枚举，**禁止把用户输入直接拼进 SQL**；
5. **幂等**：写操作考虑重复提交（后端校验 + 前端禁用）；
6. **超时**：外部 HTTP 调用必须设超时（默认 5s），**禁止无超时请求**；
7. **OpenAPI 注解**：每个端点必须有 `summary`、响应类型与错误码注解（utoipa），否则前端 codegen 拿不到类型。

### 4.3 数据层规范【原则】

1. **优先编译期校验**：能用 `sqlx::query_as!` 就用，写错列名/类型编译即失败；
2. **禁止字符串拼接 SQL**：一律参数化绑定（`bind()`）；
3. **迁移**：表结构变更必须有 `sqlx-cli` 迁移脚本，**禁止改了模型不迁移**；
4. **索引**：外键、常用筛选字段、唯一约束必须建索引（写在迁移脚本里）；
5. **软删除**：业务数据（条目、账单、笔记）默认 `deleted_at` 软删，**保留恢复能力**；
6. **事务**：跨表写用 `pool.begin()` 事务包裹，**service 层持有事务边界**；
7. **N+1**：列表 + 关联必须 JOIN 或批量查询（`WHERE id = ANY($1)`），**禁止循环里查库**；
8. **连接池**：`PgPoolOptions` 显式配置最大连接数与获取超时。

### 4.4 业务规则落点【原则】

**PRD 中每条 `RULE-xxx` 必须在 service 层有唯一实现位置**，并在注释中标注编号：

```rust
// RULE-003：单笔支出不得超过账户余额
if amount_cents > account.balance_cents {
    return Err(AppError::business(ErrorCode::InsufficientBalance));
}
```

**理由**：业务规则散落 = 改一处漏三处。标注编号后，PRD 变更能直接定位代码。

### 4.5 校验（DTO）【实现】

1. 所有入参用 serde DTO + `validator` 校验，**禁止直接读裸 `serde_json::Value` 当业务入参**；
2. 字段校验在 DTO 层（长度、范围、格式），业务校验在 service（如"余额够不够"）；
3. 数值字段必须有范围约束，字符串必须有长度上限，**禁止无上限文本字段**；
4. 枚举用 Rust `enum` + serde 重命名，**禁止裸 `String` 装状态**。

### 4.6 错误处理【原则】

1. **统一错误类型**：`thiserror` 定义 `AppError`，实现 `IntoResponse`，统一输出信封（§6.1）；
2. **领域 vs 应用层**：库/领域用 `thiserror` 明确枚举，应用组装可用 `anyhow`，但最终必须转 `AppError`；
3. **禁止吞错误**：`let _ = ...`、用 `unwrap_or_default()` 掩盖错误是红线；至少 `tracing::error!` 记录；
4. **生产慎用 `unwrap`**：`handler` 路径上禁止 `unwrap()`/`expect()`（会 panic 掉整个请求）；
5. **禁止技术细节外泄**：SQL、堆栈、内部路径**禁止出现在响应中**；
6. **错误码集中**：所有错误码在 `error.rs` 的 `ErrorCode` 枚举定义（§6.2）。

### 4.7 认证与鉴权【原则】

1. **密码**：`argon2` 哈希存储，**禁止明文、禁止 MD5/SHA1**；
2. **会话**：JWT 存 **HttpOnly + SameSite=Lax + 生产 Secure** Cookie，**禁止 localStorage 存 token**；
3. **服务端校验**：每个需权限端点必须校验（ADR-005），用 axum 中间件 + Extractor 统一；
4. **默认拒绝**：权限判断默认拒绝，显式允许才放行；
5. **会话过期**：必须对接 PRD §3.4 行为（保留现场 → 提示 → 跳登录 → 回跳）；
6. **单用户也算**：即便只有我一人用，也必须鉴权（否则暴露出去即事故）。

### 4.8 配置与密钥【原则】

1. 所有配置走环境变量（`.env` 仅本地，禁止提交）；
2. **禁止硬编码**任何密钥、数据库 URL、端口；
3. 必须提供 `.env.example`（含全部键名，不含真实值）；
4. 启动时校验必需配置齐全，**缺失即启动失败并明确报错**（不要运行时才炸）；
5. 敏感字段禁止进日志（§11.1）。

### 4.9 金额与精度【原则 · 红线级】

> 这是理财系统最容易出错、后果最严重的地方。**AI 的默认行为往往是用 `f64`。**

| 场景 | 规则 |
|------|------|
| 数据库 | `BIGINT`，单位为**分** |
| Rust 计算 | `i64`，**禁止 `f64`/`f32`** |
| 序列化 | JSON 传整数（分），**禁止传浮点** |
| 展示 | 前端格式化 `¥1,234.00`（design §6.2） |
| 字段名 | 必须带单位后缀 `_cents`，**禁止裸叫 `amount` 而单位不明** |
| 百分比/费率 | **万分比整数**（`325` = 3.25%），明确舍入规则并写测试 |
| 时间 | 存 `timestamptz`（UTC），展示转 `Asia/Shanghai` |

### 4.10 后台任务【实现】

1. 轻量任务：tokio `spawn` + 显式管理 join handle，**禁止 fire-and-forget**；
2. 定时任务用 `tokio-cron-scheduler`，**任务必须幂等**；
3. **禁止在请求路径里跑长任务**（> 3s），必须有进度反馈；
4. 任务失败必须记录 + 重试策略，**禁止静默失败**。

## 5. 前端架构规范（Next.js 16）

> 详细视觉与交互规范见 `基线-design-Web域.md`。**本节只讲架构层面的技术约束。**

### 5.1 Server / Client Component 边界【原则】

| 默认 | 何时加 `'use client'` |
|---|---|
| **所有组件默认 Server Component** | 需要 `useState`/`useEffect`、事件处理、浏览器 API、第三方客户端库 |

**硬规则**：

1. `'use client'` 只加在**真正需要的叶子组件**上，**禁止在 page/layout 顶部无脑加**（会把整棵子树推到客户端）；
2. **数据获取在 Server Component 里做**，通过 `lib/api.ts` 调后端（BFF，ADR-008）；
3. **写操作用 Server Actions**，不在客户端组件里直接调后端；
4. 传给 Client Component 的 props 必须可序列化。

### 5.2 数据获取与缓存【原则】

1. **涉及金额、账目、余额的读取默认不缓存**（必须实时），如需缓存必须显式声明原因；
2. 长列表必须分页或虚拟滚动，**禁止一次渲染上千行**；
3. 列表/筛选/分页状态**优先放 URL searchParams**（可分享、可回退、可刷新恢复）；
4. 加载态用 Suspense / loading 骨架屏，**禁止白屏等待**。

### 5.3 前端状态管理【原则】

| 状态类型 | 位置 | 规则 |
|---|---|---|
| 业务数据 | **服务端为准** | 前端不持有"真相" |
| UI 状态（展开/筛选/分页） | URL searchParams | 可分享可回退 |
| 会话凭证 | **HttpOnly Cookie**（后端签发） | ❌ 禁止 localStorage |
| 用户偏好（主题/密度） | localStorage | 非敏感，可存 |
| 重要草稿 | 服务端 | 禁止只存本地 |

### 5.4 与后端调用契约【原则】

1. **唯一出口**：所有后端调用走 `web/src/lib/api.ts`，**禁止组件里裸 `fetch(后端地址)`**；
2. **类型来自 codegen**：请求/响应类型从 `api-types.ts` 引用，**禁止手写一份重复的类型**；
3. **统一错误映射**：按 `errorCode` 映射文案（design §7.3），**禁止直接显示后端 message**；
4. **401 统一处理**：保留现场 → 跳登录 → 登录后回跳原页面；
5. **重试策略**：网络类错误重试（1s/2s/4s，最多 3 次），业务错误不重试；
6. **防重复提交**：请求期间禁用触发元素。

### 5.5 样式与 Token【原则】

1. Tailwind v4 用 **`@theme inline`** 定义 Token（**不是 `tailwind.config.js`**），Token 值**来自 design 基线 §5**；
2. **禁止写死色值/字号/间距/圆角**，一律用 Token 或 Tailwind 工具类；
3. shadcn 默认色板**必须替换为苑问色板**（松墨绿 `#4A6B57` 等），**禁止保留 shadcn 默认 slate 色**；
4. 组件必须实现五态（默认/空/加载/错误/成功，design §7.1）。

### 5.6 工程规范【实现】

1. **Biome 负责 lint + format**，提交前必须通过；
2. 严格模式开启，`any` 禁用（确有必要时写注释说明理由）；
3. `tsconfig.json` 显式处理 TS7 硬变更（§1.3）；
4. 目录按 PRD 页面 ID 组织 `app/{page}/`，便于 PRD ↔ 代码双向定位。

## 6. 前后端契约【原则】

### 6.1 统一响应信封

成功：

```json
{ "success": true, "data": { }, "errorCode": null, "message": null }
```

失败：

```json
{ "success": false, "data": null, "errorCode": "INSUFFICIENT_BALANCE", "message": "余额不足" }
```

规则：

1. `success` 与 HTTP 状态码一致（2xx → true）；
2. `errorCode` 是**机器可读的稳定标识**，前端按它映射文案；
3. `message` 是兜底文案，生产环境禁止含技术细节；
4. 列表响应必须含分页元信息：`{"items": [...], "total": 128, "page": 1, "page_size": 20}`。

### 6.2 错误码表（`server/src/error.rs`）

| 错误码 | HTTP | 前端文案 | 说明 |
|--------|------|---------|------|
| `VALIDATION_ERROR` | 422 | 请检查填写的内容 | 参数校验失败 |
| `UNAUTHORIZED` | 401 | 登录已过期，请重新登录 | 未认证 |
| `FORBIDDEN` | 403 | 没有权限执行这个操作 | 已认证但无权 |
| `NOT_FOUND` | 404 | 没找到这条内容，可能已被删除 | 资源不存在 |
| `CONFLICT` | 409 | 数据已变更，请刷新后重试 | 并发冲突 |
| `RATE_LIMITED` | 429 | 操作太频繁了，稍后再试 | 限流 |
| `INSUFFICIENT_BALANCE` | 400 | 余额不足 | 业务（示例） |
| `EXTERNAL_SERVICE_ERROR` | 502 | 外部服务暂时没响应 | 第三方依赖失败 |
| `INTERNAL_ERROR` | 500 | 服务出了点问题，已记录 | 兜底 |

**规则**：新增错误码必须同时更新 ①`ErrorCode` 枚举 ②本文档表格 ③前端映射表。

### 6.3 认证流程与过期处理【原则】

```
登录 → 后端校验 → 签发 JWT（HttpOnly Cookie）
     → 后续请求经 Next 代理自动携带 Cookie
     → 过期返回 401 UNAUTHORIZED
     → 前端：保留现场 → 提示 → 跳登录 → 登录后回跳原页面
```

**AI 提示**：**"过期后回跳原页面"是最常被漏掉的一环**，必须显式实现。

### 6.4 分页 / 排序 / 筛选【实现】

- 参数：`page`（从 1 开始）、`page_size`（默认 20，上限 100）；
- 排序：`sort=field&order=asc|desc`，**字段必须白名单枚举**；
- 筛选：显式参数（`status=active`），**禁止通用 query DSL**；
- 超过 50 行的表格必须分页（design §6.1）。

### 6.5 时间与标识【原则】

- 时间：存储与传输用 UTC（ISO 8601），展示转 `Asia/Shanghai`；
- ID：全项目统一（推荐 UUIDv7 或自增 bigint），**禁止混用**；
- 布尔：`is_` / `has_` 前缀，语义明确；
- 空值：区分 `null` 与空串，**禁止用空串表示 null**。

### 6.6 OpenAPI + 类型 codegen【实现 · 关键机制】

```
后端 utoipa 注解 → 生成 openapi.json → openapi-typescript 生成 web/src/lib/api-types.ts
                                     → 前端类型安全调用
```

规则：

1. 后端接口变更 → **必须重新生成** `openapi.json` 与 `api-types.ts`（写进 `scripts/`）；
2. `api-types.ts` 是生成物，**禁止手改**；
3. **每次改动后端接口后，前端 `tsc` 应能立刻暴露不兼容点**——这就是选 codegen 的全部价值。

## 7. 数据与备份规范【原则】

### 7.1 数据库【原则】

- 默认 **PostgreSQL**（ADR-003）；
- 实例位置、连接参数、部署方式**归实例层**（§0.0），基线不锁；
- 需要缓存（Redis 等）时**按场景决定**，实例中写 ADR 说明理由，**基线不预设缓存**。

### 7.2 迁移规范【原则】

1. 每次表结构变更必须有 `sqlx migrate add` 脚本；
2. 迁移脚本**尽量可回滚**（写 `DOWN` 段）；
3. **结构迁移与数据迁移分开**：改字段类型时写数据转换，禁止直接丢弃；
4. 正式库执行前**先备份**；
5. 迁移脚本与 `.sqlx/` **必须提交 Git**。

### 7.3 备份与恢复【原则 · 基线给原则，实例写落地】

| 项 | 基线原则 |
|----|---------|
| 备份内容 | 数据库（`pg_dump`）+ 配置文件（不含密钥）+ 代码版本（Git tag） |
| 备份频率 | **基线不锁具体频率**；原则：数据变更越频繁备份越勤（含资金数据建议日备） |
| 保留策略 | 实例中定义；原则：至少能回退到 7 天前与 1 个月前 |
| 备份位置 | **本地 + 至少一份异地**（具体介质与位置归实例层） |
| 恢复演练 | **每个项目首次上线后必须演练一次恢复**，否则备份等于不存在 |
| 备份校验 | 备份后必须校验产物可读/可导入，**禁止只导出不验证** |

> **红线**：涉及资金/资产数据的项目，**没有备份策略 = 不允许上线**（对应 PRD §11）。

### 7.4 数据精度与单位（补充 §4.9）

| 数据 | 存储 | 展示 |
|------|------|------|
| 金额 | `BIGINT` 分 | `¥1,234.00` |
| 百分比/费率 | 万分比整数（`325` = 3.25%） | `3.25%` |
| 时长 | 整数秒 | `1 小时 30 分` |
| 文件大小 | 整数字节 | `1.2 MB` |

**规则**：**所有数值字段必须在迁移脚本注释与 Rust 结构体文档中写明单位**，禁止裸数字。

### 7.5 外部中间件与依赖服务【原则 · 基线给原则，实例写清单】

> 老师版没有这一节（他的案例是纯前端单文件游戏，无外部服务）。
> 我的项目是**前后端全栈 + 中间件独立部署**，且**执行者是 AI**——
> AI 最常见的行为之一，就是假设"本机装了 PG/Redis"，并生成一堆本地安装指令作为前置条件。

#### 7.5.1 核心立场：中间件是外部独立服务

| 类型 | 举例 | 基线立场 |
|------|------|---------|
| 数据库 | PostgreSQL | **外部独立服务**，应用只通过连接配置接入 |
| 缓存 | Redis | 同上；**基线不预设是否引入**（§7.1） |
| 对象存储 | S3 / MinIO / OSS | 同上 |
| 消息队列 | RabbitMQ / Kafka / NATS | 同上 |
| 外部 API | LLM API、支付、第三方数据 | 同上 |

**原则**：

1. 中间件**不在应用进程内，不在开发机本地**——部署在内网或外网的独立服务器上；
2. 应用**只负责接入**，不负责中间件的安装、启动、运维与扩容；
3. **具体有哪些中间件、部署在哪（内网/外网/哪台机器）、地址与端口 → 全部归 `arch-A-{应用名}.md`**（§0.0）；
4. 基线只锁三件事：❶ 视为外部服务 ❷ 只验证连通性、不验证安装 ❸ 连接配置必须可注入。

> ⚠️ **别忘了 §0.0 的教训**："部署在内网"是**当前项目**的实际情况，属于实例层。
> 基线若写死"部署在内网"，将来上云就自相矛盾。**基线只写"存在外部独立服务"这个立场。**

#### 7.5.2 AI 行为硬约束（本节最重要）

| ❌ 禁止 | 具体表现 |
|--------|---------|
| 禁止在本机探测中间件"装没装" | 如 `command -v psql`、`which redis-cli`、`ps aux \| grep postgres` |
| 禁止生成本地安装/启动指令作前置条件 | 如"请先 `apt install postgresql` 并 `systemctl start`" |
| 禁止在代码或 README 中假设本机有中间件在跑 | 如硬编码 `localhost:5432`、`127.0.0.1:6379` |
| 禁止把中间件地址/端口/凭据写死 | 全走环境变量 + `.env.example`（§4.8 / 红线 3） |
| 禁止因为连不上就自行安装或改配置 | 按 7.5.4 报告，不要自己修 |

| ✅ 应该 | 具体表现 |
|--------|---------|
| 只需验证能否连通 | 按 7.5.3 的 4 步 SOP |
| 连接配置必须可从环境变量注入 | 便于切换开发/正式环境 |
| 启动失败时明确报出"哪个依赖不可用" | 禁止静默重试到超时 |

#### 7.5.3 连通性验证 SOP（基线给步骤，实例给具体值）

| 步骤 | 动作 | 期望结果 |
|------|------|---------|
| 1 | 从 `arch-A` 读取该中间件的连接配置（地址/端口/库名/凭据来源） | 配置齐全 |
| 2 | 用**最小命令**验证连通（不查业务数据、不改数据） | 能连上 |
| 3 | 验证**最小权限动作**（如 `SELECT 1` / `PING` / `HEAD bucket`） | 返回成功 |
| 4 | 把结果记录进 `arch-A` 的「连通性验证」小节 | 有记录可追溯 |

> **判定标准只有一条：能连上就能开发，连不上就是环境问题。**
> **不需要在本机安装任何中间件，也不需要确认它"装没装"。**

#### 7.5.4 连不上时的处理

1. **视为环境问题，不是代码问题** → 报告给用户（说明哪个中间件、什么现象），**不要自行安装或篡改配置**；
2. 应用启动必须有**明确的依赖不可用报错**（指明是哪个中间件），禁止静默重试到超时；
3. **降级策略归实例**：是否允许无缓存降级启动、是否有兜底，写在 `arch-A` 里（参见 §10.2）。

#### 7.5.5 基线与实例的分工

| 项 | 基线（本文档） | 实例（arch-A） |
|---|---|---|
| 中间件清单（本项目用哪几个） | ❌ 不锁 | ✅ 逐个列出 |
| 部署位置（内网 / 外网 / 哪台机器） | ❌ 不锁 | ✅ 写明 |
| 地址、端口、库名、凭据来源 | ❌ 不锁 | ✅ 写在 `.env.example` |
| 是否引入缓存（Redis） | ❌ 不预设 | ✅ 按场景决定并写 ADR |
| **"中间件 = 外部独立服务"的立场** | ✅ 锁 | — |
| **"禁止本机探测/安装"的行为约束** | ✅ 锁 | — |
| **连通性验证的 4 步 SOP** | ✅ 锁 | 填具体命令与结果 |

## 8. 安全规范【原则】

### 8.1 认证与授权

1. 密码 `argon2` 哈希；2. 登录失败限流；3. 敏感操作（改密码、删除、导出）二次确认；4. **服务端强制鉴权**（ADR-005）。

### 8.2 输入校验与注入防护

1. 所有用户输入必须经 DTO 校验；
2. **禁止字符串拼接 SQL**（`bind()` 参数化）；
3. 文件上传：限制类型/大小/重命名，**禁止用原始文件名拼路径**；
4. 重定向参数必须白名单校验（防开放重定向）；
5. React 默认转义，**禁止用 `dangerouslySetInnerHTML` 渲染用户输入**（确需则先 sanitize）。

### 8.3 敏感数据与日志脱敏

1. 日志中**禁止输出**：密码、Token、API Key、身份证/银行卡号、完整手机号；
2. 展示脱敏：中间位掩码（`138****8888`）；
3. 导出功能必须有权限校验 + 审计记录；
4. 与 PRD §11 数据合规章节**逐条对齐**。

### 8.4 传输与部署安全

1. 涉及登录/敏感数据**必须 HTTPS**；
2. 安全响应头（`X-Content-Type-Options`、`X-Frame-Options`、`CSP`）；
3. Cookie：`HttpOnly` + `SameSite=Lax` + 生产 `Secure`；
4. **禁止把服务直接暴露公网而不鉴权**；
5. 依赖定期更新（`cargo audit` / `cargo deny`、npm audit）。

### 8.5 依赖与供应链（OPC 版 · 重要）

1. **依赖越少越好**：引入前先问"能不能用标准库 20 行解决"；
2. Rust crate 引入必须检查：维护活跃度、是否有 unsafe 滥用、许可证；
3. 锁定版本（`Cargo.lock` **必须提交**；npm 用 lockfile）；
4. **AI 推荐的新依赖，必须先告诉我它是什么、为什么需要，我批准后才能引入。**

## 9. 性能基线【原则 · 基线给指标类别，实例给具体数值】

| 指标类别 | 基线原则 |
|---------|---------|
| API 响应（简单查询） | 实例中定义 P95 目标；**必须可测量**（tracing 计时） |
| API 响应（列表/聚合） | 同上，且必须分页 |
| 首屏加载 | 实例中定义；原则：< 2s（本地/内网） |
| 数据库查询 | **单页查询数 < 20**（防 N+1，SQL 日志可验证） |
| 内存 | 无持续增长（Rust 侧关注 Arc 循环与未释放连接池） |

**规则**：

1. 列表接口必须分页；
2. 聚合/统计走 SQL 聚合，**禁止拉全量进 Rust 内存计算**；
3. 慢查询必须有索引支撑，索引写在迁移脚本里；
4. 静态资源走缓存（Next 默认处理 hash 文件名）。

## 10. 错误处理与降级【原则】

### 10.1 错误分类与处理

| 错误类型 | 后端 | 前端 |
|---------|------|------|
| 校验失败 | 422 + 字段级错误 | 输入框下方显示原因 |
| 认证过期 | 401 UNAUTHORIZED | 保留现场 → 跳登录 → 回跳 |
| 权限不足 | 403 FORBIDDEN | 提示 + 引导，不显示技术信息 |
| 业务冲突 | 409 CONFLICT | 提示刷新重试 |
| 外部依赖失败 | 502 + 降级 | 局部错误态 + 重试 |
| 系统异常 | 500 + 记录日志 | 通用错误态 + 可返回 |

### 10.2 降级策略

1. **外部依赖必须有降级**；2. **局部失败 ≠ 整页失败**；3. 核心功能不可用要有明确提示，不能白屏；4. **禁止静默失败**（重试/提示/记录，三者至少占一）。

## 13. 部署与运维规范【原则】

> 一人公司运维原则：**能自动的绝不手动，能一条命令的绝不用三条。**
> ⚠️ **具体部署拓扑（WSL / 云 / NAS / Docker）归实例层，本节只给原则。**

### 13.1 启动

1. 每个项目必须有启动脚本（`scripts/start.sh`）；
2. 启动脚本必须：检查依赖 → 检查配置（缺 `.env` 提示复制模板）→ 运行迁移 → 启动服务；
3. README 必须写清：如何启动、如何备份、如何恢复、如何升级。

### 13.2 发布流程

```
本地开发 → 自测（§16 清单）→ 提交 Git（打 tag）
        → 备份数据库 → 应用迁移 → 发布新二进制/前端 → 冒烟验证核心路径 → 完成
```

### 13.3 回滚

1. **代码回滚**：`git checkout <上一个 tag>` 并重新构建；
2. **数据回滚**：从备份恢复（**必须先演练过**）；
3. **迁移回滚**：`sqlx migrate revert`；
4. **顺序**：停服务 → 回滚代码 → 回滚数据 → 启动验证。

### 13.4 进程与守护

- 服务崩溃必须能自动重启（systemd / 容器 restart policy，**具体方式归实例层**）；
- Rust 二进制为单文件，优先直接跑 + 守护，不为了容器化而容器化。

## 15. 代码规范【原则】

### 15.1 Rust 命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 模块/文件 | snake_case | `account_service.rs` |
| 类型/结构体 | PascalCase | `AccountService` |
| 函数/变量 | snake_case | `get_balance()` |
| 常量 | UPPER_SNAKE_CASE | `MAX_PAGE_SIZE` |
| 数据库表 | 复数 snake_case | `transactions` |
| 金额字段 | `{name}_cents` | `amount_cents` |
| 布尔字段 | `is_` / `has_` | `is_deleted` |
| 时间字段 | `_at` | `created_at` |
| API 路径 | 复数小写中划线 | `/api/v1/transactions` |

### 15.2 TypeScript / React 命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 组件文件 | PascalCase.tsx | `TransactionList.tsx` |
| 非组件模块 | kebab-case.ts | `format-currency.ts` |
| 组件名 | PascalCase | `<TransactionList />` |
| 变量/函数 | camelCase | `formatCurrency()` |
| 类型 | PascalCase，不加 `I` 前缀 | `Transaction` |
| 常量 | UPPER_SNAKE_CASE | `DEFAULT_PAGE_SIZE` |

### 15.3 注释

1. 注释说明**为什么**，不描述**是什么**；
2. **业务规则必须标注 PRD 编号**（`// RULE-003: ...`）；
3. 非直觉处理（为什么加锁、为什么要这个超时）必须注释；
4. 禁止大段注释掉的代码（Git 有历史）。

### 15.4 类型与契约

1. Rust：公开函数签名必须有完整类型，禁止在关键结构上滥用 `serde_json::Value`；
2. TS：`strict` 开启，**禁用 `any`**（确有必要时写注释说明理由）；
3. 前后端共享类型**只能来自 codegen 产物**（§6.6），禁止两边各写一份。

### 15.5 设计 Token 引用（与 design 基线咬合）

1. **禁止写死色值**，必须引用 `@theme` 中的 Token；
2. 禁止写死字号、间距、圆角；
3. 组件必须实现五态。

## 17. AI 生成代码的硬约束（苑问特有 · Rust + Next 版）

> 老师版没有这一章（他面向人类团队）。**我的执行者是 AI，而 AI 写 Rust 与 Next 有固定翻车模式。**

### 17.1 AI 写 Rust 后端最常见的 11 个错

| # | AI 常见的错 | 硬约束 |
|---|------------|--------|
| 1 | 业务逻辑全写在 handler 闭包里 | **强制分层**（§4.1），规则进 service 并标 RULE 编号 |
| 2 | 金额用 `f64` | **`i64` 分**，float 参与金额即缺陷（§4.9） |
| 3 | 只前端隐藏按钮，后端不校验 | **服务端强制鉴权 + 越权测试用例**（ADR-005） |
| 4 | 密码明文 / MD5 | `argon2` 哈希（§8.1） |
| 5 | 密钥、数据库 URL 硬编码 | 全走环境变量 + `.env.example`（§4.8） |
| 6 | `let _ = ...` / `unwrap_or_default()` 掩盖错误 | 禁止吞错误，必须分类处理并记录（§4.6） |
| 7 | 改了模型不写迁移 | 表结构变更必须带 sqlx 迁移（§7.2） |
| 8 | 列表全表返回、循环里查库 | 必分页 + JOIN/批量查询防 N+1（§4.3） |
| 9 | 用 `println!` 调试 | 用 `tracing` + request_id（§11.1） |
| 10 | 顺手引入一个没见过的 crate | **依赖白名单，引入前必须问我**（§1.1 / §8.5） |
| 11 | 假设本地有 PG/Redis，生成安装指令作前置条件 | **中间件 = 外部独立服务，只验证连通性**（§7.5） |

**额外两条 Rust 特有**：

- **滥用 `unwrap()`/`expect()`** —— handler 路径上 panic 会打挂请求，必须转 `AppError`；
- **用 `String` 装状态/枚举** —— 必须用 Rust `enum` + serde 重命名。

### 17.2 AI 写 Next 前端最常见的 9 个错

| # | AI 常见的错 | 硬约束 |
|---|------------|--------|
| 1 | 在 `page.tsx` 顶部无脑加 `'use client'` | **默认 Server Component**，只在叶子加（§5.1） |
| 2 | 组件里裸 `fetch('http://localhost:xxxx/...')` | **必须走 `lib/api.ts`**（ADR-008） |
| 3 | 手写一份与后端重复的类型 | **类型必须来自 codegen**（§6.6） |
| 4 | 把 token 存 localStorage | HttpOnly Cookie（§5.3） |
| 5 | 写死色值 `#xxx`、奇葩像素 `13px` | 全部 Token（§5.5） |
| 6 | 保留 shadcn 默认 slate 色板 | **必须替换为苑问色板**（§5.5） |
| 7 | 401 直接踢到登录页不回跳 | 必须保留现场 + 回跳（§6.3） |
| 8 | 列表一次渲染上千行 | 分页或虚拟滚动（§5.2） |
| 9 | 视觉规范写"靠感觉"的词（如"颜色再柔和点"） | **必须可被 axe-core / computed style 判定**（§14.4 / design §10.1） |

### 17.3 给 AI 的生成指令（可直接复制）

```
在写任何代码之前，先读取并执行 `基线-arch-Web域.md`（Rust + axum / Next.js 16 全栈版）：

【后端 Rust】
1. 分层：handler 只做协议转换，业务规则必须写在 service 层，
   注释标注 PRD 规则编号（如 // RULE-003）。
2. 金额：数据库 BIGINT 存分（字段 xxx_cents），Rust 侧 i64 运算，
   全链路禁止 f64/f32。展示层才格式化为 ¥。
3. 权限：每个需权限端点必须服务端校验，前端隐藏按钮不算数；
   每个权限点写一条越权测试（期望 403）。
4. 数据：优先 sqlx::query_as!（编译期校验），禁止字符串拼接 SQL；
   列表必分页；关联用 JOIN 或批量查询防 N+1；.sqlx/ 必须提交。
5. 配置：密钥/数据库 URL/端口全走环境变量，禁止硬编码；
   同步更新 .env.example（只含键名）。
6. 错误：业务错误转 AppError(ErrorCode::X)，走统一响应信封；
   禁止 let _ = 吞错误；handler 路径禁止 unwrap；禁止把堆栈/SQL 返回前端。
7. 日志：tracing（禁止 println!），含 request_id，禁止输出敏感原文。
8. 迁移：表结构变更必须带 sqlx 迁移脚本，且 revert 可用。
9. 依赖：只能用 §1.1 清单内的 crate；需要新 crate 先停下来问我。
10. 中间件：PG/Redis 等一律视为**外部独立服务**（§7.5）——
    禁止在本机探测装没装、禁止生成安装指令作前置、禁止假设 localhost 上有中间件；
    只需验证能否连通，连不上就当作环境问题报告给我，不要自行安装。

【前端 Next】
10. 组件默认 Server Component，'use client' 只加在真正需要的叶子组件。
11. 所有后端调用走 src/lib/api.ts，禁止裸 fetch 后端地址。
12. 类型从 api-types.ts（codegen 产物）引用，禁止手写重复类型。
13. 样式用 Token（Tailwind v4 @theme），禁止写死色值；
    shadcn 默认色板必须替换为苑问色板（主色 #4A6B57）。
14. 401 必须保留现场 + 登录后回跳原页面。
15. 金额展示：千分位 + 两位小数 + 等宽数字；涨跌红涨绿跌且带 +/- 号。
16. 视觉与无障碍规范（对比度、热区、焦点态）必须**可被自动验证**——
    禁止写"颜色再柔和点"这类无法判定的描述；
    核心页面需通过 axe-core 扫描与 computed style 断言（§14.4）。
17. 完成后对照 §16 代码审查清单逐项自查，输出 ✅/❌ 与说明。
```

11. **禁止列表接口不分页或全表返回**；

19. **禁止核心页面未经自动扫描即交付**（axe-core / computed style，§14.4）。
