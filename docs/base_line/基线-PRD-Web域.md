# PRD 模板规范（prd.md）—— 苑问 · **Web 域** v0.2

> 版本：v0.2
> 生效日期：2026-09-07
> 维护人：苑问（OPC 一人公司）
> **适用范围：浏览器访问的 Web 应用（前后端）** —— 含可套壳为桌面应用的 Web 项目
> 典型项目：家庭知识库、理财系统、生活工作台等
> 关联基线：`基线-arch-Web域.md` v0.2 / `基线-design-Web域.md` v0.1（由具体需求填写版本）
> 参考来源：企业 AI 编程行动营 L01 · X学科技 prd.md v4.0；苑问母版 v0.2

> **本文档的第一读者是 AI，第二读者是我自己。** 所有【AI提示】都是给 AI 的执行线索，填写时不要删除。
> **其他域（小程序 / 移动 APP / AI 应用 / 数据服务 / C 系统作品 / 数仓需求）各自建基线，不套用本模板。**

## ⚠️ 适用范围收窄为 Web 域（v0.2）

| 形态 | 归哪份基线 |
|---|---|
| **Web（浏览器访问）** | **本文件** + `基线-design-Web域.md` + `基线-arch-Web域.md` |
| 小程序 / 移动 APP | ❌ 不在本域，**将来另建一套三基线**（照本套结构抄） |

**为什么三份基线统一按 Web 域建**：小程序 / 移动 APP 在**需求结构、视觉规范、技术栈与代码组织**三层上与 Web 都存在足够大的差异（构建、路由、审核、跨端框架、Token 实现方式），
任何一层硬塞"跨端"都会让基线写得含糊。**先把 Web 这一套三基线打磨到 90 分，将来真有小程序/APP 需求时整套另起一份三基线**——
这比维护一份"名义跨端、实则写得含糊"的基线更有效（基线是被项目喂大的，不是设计出来的）。

## 0. 模板使用说明

### 0.1 定位

本文档是「苑问的 Web 类需求应该怎么写」的母版规范。每个 Web 类需求必须基于本模板产出 `prd-{应用名}.md`，不得删减标注为【必填】的章节。

**本域的共同特征**：浏览器访问、有界面、有用户、有交互、需要长期运维。因此本模板在通用结构之外，强化了**用户与权限、界面状态、响应式适配、体验指标、用户数据合规**五块。

### 0.2 交付形态（Form）【必填】

本域内"长什么样"的类型。形态决定技术选型与 §8/§9/§12 的写法：

| 形态代码 | 形态 | 典型技术栈 | 对本文档的影响 |
|---------|------|-----------|-------------|
| `WEBAPP` | **Web 应用（前后端）—— 默认** | Rust + axum / Next.js 全栈 | 标准填写；§9.2 写浏览器兼容 |
| `SPA` | 纯前端单页 + 公共后端/第三方服务 | Next.js / Vite SPA | §9.2 写浏览器兼容；§11 需说明数据存放方 |
| `STATIC` | 静态站点 | 静态托管，无自建后端 | §9.1 简化；§12 可降级为可选 |
| `DESKTOP` | 桌面应用（Web 套壳） | Tauri / Electron 包裹 Web | §8 写窗口与交互；§9.2 写操作系统 |

**填写格式**：`交付形态：WEBAPP`（多形态则列出全部，标注主形态）

> 说明：**小程序 / 原生 APP 不在本域**。若某需求确实要做小程序端，在 §5 Out of Scope 注明"本 PRD 只覆盖 Web 端"，小程序端另建 PRD 与基线。

### 0.3 填写规范

| 标记 | 含义 | 处理规则 |
|------|------|---------|
| 【必填】 | 必须填写，不可为空 | 缺失则**不允许进入 Plan 阶段** |
| 【推荐】 | 强烈建议填写 | 可空，但需在自检时说明原因 |
| 【可选】 | 视需求复杂度决定 | 简单需求可省略 |
| 【AI提示】 | 给 AI 的辅助提示 | 人类填写时参考，**AI 执行时重点读取** |

### 0.4 合格验收标准（自检用，AI 与我都要过）

1. 所有【必填】字段已填写，无空项；
2. 至少 1 条核心用户故事，每条至少 1 条 GWT 验收标准；
3. 覆盖**正常 / 异常 / 边界**三类场景各至少 1 条 AC；
4. Out of Scope 明确列出，不得为空；
5. 至少 1 组真实数据示例；
6. 已声明交付形态、目标平台/环境、关联基线版本；
7. §3 用户与权限已定义（**即便只有"我自己"一个角色也要写清**）；
8. §8.3 页面状态矩阵覆盖五态（默认/空/加载/错误/成功）；
9. §11 数据合规与隐私已逐项评估（**不允许只写"不涉及"而不给理由**）；
10. 变更记录中 v0.1 的「变更内容」不为空；
11. **无未量化形容词**（"快""友好""流畅""强大"必须替换为数字或场景）。

### 0.5 形态差异速查表

| 章节 | WEBAPP | SPA | STATIC | DESKTOP |
|------|--------|-----|--------|---------|
| §3 用户与权限 | 必填 | 必填 | 推荐 | 推荐 |
| §8.1 平台限制列 | 不需要 | 不需要 | 不需要 | **必填**（窗口/系统能力） |
| §8.5 响应式适配 | **必填** | **必填** | 必填 | 可选（固定窗口时） |
| §9.1 性能 | 必填 | 必填 | 简化 | 推荐 |
| §9.2 兼容性 | 浏览器及版本 | 浏览器及版本 | 浏览器及版本 | 操作系统 |
| §9.5 埋点 | 必填 | 必填 | 推荐 | 推荐 |
| §12 设计需求 | 必填 | 必填 | 可选 | 必填 |

### 1.1 优先级定义

| 优先级 | 定义 | 响应方式 | 典型场景 |
|--------|------|---------|---------|

### 1.3 完成定义（DoD）模板【必填】

【AI提示：DoD 是"做完"的标志，必须可判定。Web 类需求的 DoD 至少覆盖功能、体验、数据、运维四块。】

```
- 数据：埋点事件已上报并可查（列出事件名）

- 我的验收动作：<如"我自己连续用 3 天，每天至少 1 次核心流程">
```

## 附录 B：FAQ（Web 域版）

**Q1：家庭自用的小应用也要写这么全？**

> 结构不能省，内容可浅。**必填章节一个都不能少**，但每条可以只写一行。理由：执行者是 AI，你漏一节，AI 就在那节自由发挥——而自由发挥的返工成本远高于你多写一行。
> 真正能省的是：§5.3 未来规划、§9.6 成本（纯本地运行时填"无外部付费资源"）、§8.5 多端一致性（单端时填"不适用"）。

**Q2：AI 生成的 PRD 我要自己过一遍吗？**

> 必须。这 6 项**必须我亲自确认**：问题陈述是否真实、成功指标是否可量化、业务规则、Out of Scope、权限矩阵、数据合规判断。**这是 AI 最容易编造的地方。**

**Q3：做着做着需求变了怎么办？**

> 追加变更记录（§13）并升版本号。若变更影响**业务规则、权限模型或数据合规**，必须回到 §4 重审 AC，并重新走一遍附录 A。

**Q4：模板里的【AI提示】要删吗？**

> **不要删。** 保留能显著提升 AI 执行质量——这是给 AI 的"字段语义说明"。

**Q5：为什么 PRD 里不能写接口、表结构、框架选型？**

> 因为 PRD 是"做什么"，技术实现是"怎么做"。分开的好处：**技术栈升级时 PRD 一字不用改**（老师的 arch.md 从多文件方案切到单文件方案时，PRD 未动）。技术实现写在 `arch-A-{应用名}.md`。

**Q6：我还有其他业务（AI 工具 / 数据服务 / C 项目）怎么办？**

> **各自建自己的 PRD 基线**，不套用本模板。本模板是为"有界面、有用户"的应用定制的——给 C 库或数据管道用会很别扭（它们没有页面、没有登录）。
> 建新域基线时**照抄本文档的骨架**（0 说明 / 1 元信息 / 2 背景 / 3 域核心章节 / 4-6 故事·范围·规则 / 7 数据 / 8 流程 / 9 NFR / 10 风险 / 11 合规 / 12 域特定 / 13 变更 / 附录），把 §3 和 §8 换成那个域的核心章节即可。**母版参考见 `基线-PRD-母版参考-待按域拆分.md`。**

**Q7：这份基线上限怎么提高？**

> 每次项目结束后回补。信号很明确：**AI 在 Plan/Code 阶段问我"A/B/C 选哪个"，就说明这里基线写得不够清楚**，把它写回模板。版本演进记录在文件头。
