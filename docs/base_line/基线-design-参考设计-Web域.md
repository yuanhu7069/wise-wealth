# 设计基线（参考设计引入型）—— 苑问 · Web 域 v0.1

> 版本：v0.1（**初稿阶段，修订不升版本**）
> 生效日期：2026-09-17
> 维护人：苑问（OPC 一人公司）
> 关联：`基线-PRD-Web域.md` / `基线-arch-Web域.md`

> **用途**：当某个项目要**参考 / 模仿现有成熟产品的设计**时，由**我**把本文档交给 AI。
> **给 AI 的指令（最高优先）**：**本文档是本项目的 design 基线，界面设计严格遵循本文档。**

> **本文档的第一读者是 AI，第二读者是我自己。**
> 本基线**不定义任何视觉内容**——那些来自参考设计本身。它只管一件事：**从选定参考到落地声明的全过程治理**。

## 0. 定位与使用方式

**本文档是本项目的 design 基线**——界面设计严格遵循本文档。

### 0.1 边界（与另外两份基线的分工）

| 文档 | 管什么 | 不管什么 |
|------|--------|---------|
| `基线-PRD-Web域.md` | 做什么、为谁做、做到什么算完 | 长什么样、用什么技术 |
| **本文档（design）** | **界面参考谁、抄了什么、允许改什么** | 代码结构、技术栈、数据存储、接口设计；**具体视觉值**（那些来自参考设计本身） |
| `基线-arch-Web域.md` | 用什么技术、怎么组织代码、性能与安全红线 | 视觉与交互细节 |

**三条硬边界**：
1. 本文档**不写技术选型**（框架、组件库、状态管理、构建方式）——那些归 arch；
2. 本文档**不写业务规则**（什么能做什么不能做）——那些归 PRD；
3. 本文档**只做一件事**：让 AI **抄得准、抄得可追溯、抄完之后改不坏**。

### 0.2 适用范围

- **适用**：明确要**参考 / 模仿某个成熟产品的视觉与交互**的项目——对外展示、作品背书、需要专业观感但自己定不出数值的场景。
- **不适用**：不参考任何成熟产品的项目（无参考对象，本文档无可治理的内容）。

### 0.3 本文档不覆盖的内容（需要时由我给，AI 不得自行套用）

本文档**只覆盖视觉来源治理**，不含：
- 验收清单、AI 硬约束、变更记录等**流程性内容**；
- Token 与视觉规则**本身**（色值、字阶、间距——那些来自参考设计）。

> 若本项目确实需要这些，**由我在实例文档中给出**；
> AI **不得自行从其他来源套用**，也不得假设存在某份"默认文档"可以参照。

## 1. 采用原则：全盘复制，调节在实例

> **本基线不替实例做取舍。一旦选定参考设计，默认全盘采用**——色值、字体、装饰、版式，一律照参考来。
> 需要调节的地方，**在实例文档的调整清单（§2.2）中逐条声明**；**本基线不做预先限制**。

**为什么不在基线里规定「借什么不借什么」**：

「该借什么、不该借什么」取决于**这个具体项目是什么页面、给谁用**——营销页和数据后台的答案完全相反。换一个项目结论就变，按边界元规则（**换一个项目，这条还成立吗**），**这类判断归实例层，不归基线层**。
基线若预先划线（如「装饰一律不借」），会把「万一人家就合适」的情况直接堵死。

### 1.1 已知需在实例中确认的点（提醒清单，**不是禁令**）

默认仍按参考执行；列出只表示这几项实测容易踩坑：

| # | 项 | 为什么建议确认一下 |
|---|---|---|
| 1 | 商业字体是否可用 | 参考设计常用商业授权字体（如 Sohne）；拿不到会静默 fallback，出现「文档写 A、实际渲染 B」 |
| 2 | 颜色有没有承载规则 | 参考设计多用品牌命名（如 `ink` / `ruby`），名字不承载任何规则。若本项目有**靠颜色表达语义**的场景（涨跌方向、状态等级、风险提示），必须在 §2.2 中显式指定色值与规则，否则 AI 无从判断 |
| 3 | 装饰密度与页面类型是否匹配 | 营销页可为氛围牺牲信息密度，数据密集型后台通常相反。**取决于本项目页面是「让人干活」还是「让人被说服」**——由实例判断 |
| 4 | 中文字重与字距是否要加档 | 参考设计多为英文产品，常见「细体大标题 + 负字距」；中文场景（Windows 无 PingFang、微软雅黑细体偏糊）通常需加重一档、字距收敛 |

> 以上四项**默认按参考设计执行**；只有当我判断不合适时，才在 §2.2 中声明调整。

## 2. 声明模板（由实例文档填写）

### 2.1 来源追溯

| 项 | 填写 |
|----|------|
| 主参考来源 | `<registry 路径 或 GitHub 路径>` |
| 版本锚点 | commitSha / tag |
| 拉取日期 | YYYY-MM-DD |
| 局部参考（可选） | `<组件或页面>: <来源>` |
| 原始件存放位置 | `docs/design-ref/<name>.md`（**参考件，非项目真源**） |

### 2.2 本地化调整清单（逐条列）

> **参考设计就是本项目的唯一视觉真源**——色值、字阶、间距、装饰，一切以它为准。
> 本表记录的是**我对参考设计本身做了哪些改动**。

| 调整项 | 参考设计原值 | 本项目值 | 理由 |
|--------|------------|---------|------|
| 例：字阶档数 | 8 档 | 6 档 | 页面信息量小，用不到那么多档 |
| 例：主色 | `#533AFD` | `#4A6B57` | 品牌色须与我的其他产品一致 |

- **未列入本表的项一律照参考设计执行，AI 不得自行发挥**；
- 验收判定：**实现结果与参考设计不一致之处，必须能在表中找到**；找不到的即为违规。

> ⚠️ **AI 可见性**：AI 生成界面时读的是 `DESIGN.md`，不是本声明所在的实例文档。
> 因此本表**必须有一份精简版写进 `DESIGN.md` 正文末尾**，否则 AI 看不到，等于没有授权。

### 2.3 断源状态（P0 · 防止改造结果被覆盖）

| 项 | 填写 |
|----|------|
| 断源状态 | 已断源 / 未断源 |

- 若用 `designmd.sh` 管理：其 `update` 命令**从源重新拉取并覆盖本地文件**，无视本地修改；
- 对**已改造**的 `DESIGN.md`：必须置为「**已断源**」，或原始件与改造件分开存放；
- **禁止对改造过的文件执行 `update`**；
- `design-lock.json`（记录来源与 commitSha）**必须纳入 Git**。

## 3. 工具与命令

> **DESIGN.md** 是 Google 提出的视觉身份描述格式（YAML frontmatter 存 token + 正文 8 段写 rationale），目前为 **alpha**（`@google/design.md` v0.4.0）。

| 工具 | 是什么 |
|------|--------|
| `designmd.sh` | DESIGN.md 公共 registry + CLI（VoltAgent）：`add` 拉取、`validate` 校验（**内置 Google linter，无需另装**）、`update` 从源重拉 |
| `@google/design.md` | 格式规范 + lint / diff / export |

```bash
# 1. 拉参考件，存为「参考件」而非项目真源
npx designmd.sh add voltagent/awesome-design-md/design-md/stripe \
  --output docs/design-ref/DESIGN.stripe.md

# 2. 改造后写进 ./DESIGN.md

# 3. 校验（有 error 时 exit 1，可直接挂 CI 门禁）
npx designmd.sh validate ./DESIGN.md

# 4. 导出为 Tailwind v4 CSS 变量（接 arch 基线技术栈 Tailwind 4.3.3）
npx @google/design.md export --format css-tailwind DESIGN.md > theme.css
```

**已知事项**：

- `add` 默认写 `./DESIGN.md`，`--output` 可改；已存在时询问 save-as / overwrite / cancel
- Windows / PowerShell 下包名带 `.md` 有坑，用 `npx -p @google/design.md designmd lint`；**WSL 无此问题**
- 规范仍为 alpha，**不要把任何基线与它绑死**

### 3.1 参考来源选择建议（非强制）

registry 里大多是**品牌营销页**（Nike / SpaceX / Ferrari 等），与后台 / 工具类应用错配。按项目类型挑：

| 项目类型 | 建议参考 | 说明 |
|---------|---------|------|
| 金融 / 数据密集（理财、统计） | `stripe` > `airtable` > `linear-app` | 金融基建、可信感、高密度克制 |
| 内容 / 知识库（长文阅读） | `notion` > `mintlify` | 长文阅读舒适度 |
| 工具型后台 | `linear-app` / `vercel` / `raycast` | 高密度、无装饰 |

> **我不擅长审美判断，所以不靠「好不好看」挑，靠「这个页面是干什么用的」挑**：
> 让人**干活 / 看数据** → 密度优先；让人**被说服 / 注册** → 氛围优先。
> 前者是事实问题，后者是我判断不了的主观问题。
